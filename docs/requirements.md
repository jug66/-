## 1. 项目目标与使用场景

### 1.1 项目目标

建设一个可通过桌面和手机浏览器使用的独立留言板。访客可以阅读讨论，注册用户可以发起留言、回复任意有效留言，并删除自己的内容。

最重要的结果有三项：

1. 对话关系准确：能够持续回复，不把深层回复错误归到顶层。
2. 数据规模增长时仍可逐步浏览：页面不要求一次取回和展示整场讨论。
3. 删除行为明确：作者删除自己的内容时，不破坏其他用户的已有回复和对话关系。

### 1.2 贯穿全文的场景

```text
A，小王：周末去哪里？
├─ B，小李：可以去公园。
│  └─ C，小张：哪个公园？
│     └─ D，小李：市中心的那个。
└─ E，小赵：我想去图书馆。
```

在这个场景中：

- A 是顶层留言，也是这场讨论的根。
- C 直接回复 B，而不是直接回复 A；D 直接回复 C。
- 用户展开 A 时可以先看到 B、E；展开 B 时再加载 C。
- 小李删除 B 后，B 显示“该留言已删除”，C、D 保留。
- 小张仍可继续回复有效的 C 或 D，但不能直接给已删除的 B 新增回复。

### 1.3 成功标准

第一版完成标准是：所有首版功能需求和对应验收场景通过，原始要求全部可追溯；查询、并发及深层展示有实际测试证据；未完成的扩展单独列示。

本文件中的测试规模和响应时间均为后续验证要求或候选目标，不能作为系统已经具备这些性能的证明。

### 2.3 第一版不包含

多留言板、多租户、私信、账号注销、用户改名、内容编辑、恢复已删除正文、评论移动、普通作者删除整棵子树、精确的全体后代计数、实时多人同步。

这些边界用于避免将基本留言板扩展成完整社区产品。新增需求应说明用户价值，并评估对权限、查询、状态和验收的影响。

## 3. 用户角色与权限

| 能力 | 未登录访客 | 已登录用户 | 内容作者 | 管理员，P1 |
| --- | --- | --- | --- | --- |
| 阅读有效留言、删除占位及可见回复 | 允许 | 允许 | 允许 | 允许 |
| 注册、登录 | 允许 | 已登录时提示当前身份 | 同已登录用户 | 使用已有管理身份 |
| 发布顶层留言 | 不允许 | 允许 | 允许 | 允许 |
| 回复任意 active 留言 | 不允许 | 允许 | 允许 | 允许 |
| 直接回复 deleted 留言 | 不允许 | 不允许 | 不允许 | 默认也不允许 |
| 删除自己的有效留言 | 不允许 | 作为作者时允许 | 允许 | 允许 |
| 删除他人的内容 | 不允许 | 不允许 | 不允许 | 按独立管理规则处理 |
| 删除自己留言下其他人的回复 | 不允许 | 不允许 | 不允许 | 后续单独定义治理权限 |

## 4. 业务规则与默认参数

### 4.1 核心规则

| 编号 | 规则 | 解释 |
| --- | --- | --- |
| BR-01 | 单个公共留言板，读写权限分离 | 未登录可阅读，写入必须登录 |
| BR-02 | 无限层级指业务不设置固定最大回复层数 | 任意 active 节点可被回复；不要求单请求加载无限数据 |
| BR-03 | 真实父关系不可随意改写 | 直接父节点表示真实回复对象；不能为了布局把深层回复扁平化存储 |
| BR-04 | 删除只清空本条内容 | 保留 ID、作者关联、创建时间、父／根关系及删除状态，子回复不动 |
| BR-05 | 已删节点不能接收新回复，有效后代仍可接收 | B 删除后不能回复 B，可以继续回复仍 active 的 C、D |
| BR-06 | 在同级范围内按时间排序 | 根之间排序，每个父节点的直接子节点之间排序；不打散整棵树做全局时间线 |
| BR-07 | 身份和时间以服务端为准 | 作者来自会话，创建时间由服务端产生；不信任客户端自报 |
| BR-08 | 节点状态与加载状态分开 | 节点只有 active／deleted；未加载、加载失败、折叠是页面状态 |
| BR-09 | 仅在服务端确认保存后反馈成功 | 请求超时代表结果不明，不能直接认定未保存，也不能直接再建一条 |
| BR-10 | 保留占位不等于保留原文 | 删除后公共接口不返回旧正文；身份匿名化、账号注销另行设计 |

第一版保留所有删除占位，包括没有回复的叶子和已经全部删除的分支。暂不自动清理这些结构，以免引入额外的分页、引用和并发规则。

### 4.2 本版默认值

下表数值属于本版建议，可配置或评审调整；不是原始需求给定的限制。

| 参数 | 默认规则 | 调整影响 |
| --- | --- | --- |
| 登录名 | 3～32 个 ASCII 字母、数字或下划线；去掉首尾空白后按小写归一化；归一化值唯一 | 改变现有账号匹配和唯一性规则时需迁移 |
| 显示名称 | 1～30 个 Unicode 码点，去掉首尾空白；允许重名；可留空并默认使用登录名 | 显示名称不得用于判断所有权 |
| 密码 | 9～128 个 Unicode 码点；允许空格，不自动去掉空白，不强制字符类别组合；拒绝常见密码 | 两端校验一致；敏感字段不得回显或记录；详见账号与注册管理需求 |
| 留言正文 | 1～2000 个 Unicode 码点；拒绝全空白；允许换行，保留正文排版 | 字符限制与请求体字节限制分别校验 |
| 创建／回复请求体 | 最大 32 KiB，超出拒绝 | 为整体请求设置资源预算，不替代正文长度校验 |
| 根列表 | 默认每次 20 条，最大 100 条 | 非法或超限参数应明确拒绝，不回退为全量 |
| 直接回复列表 | 默认每次 20 条，最大 100 条 | 各父节点独立分页 |
| 默认排序 | 根：新到旧；同父直接回复：旧到新 | 第一版只有根排序提供切换；子回复方向固定 |
| 会话 | 空闲 30 分钟过期，绝对有效期 7 天 | 由有效鉴权请求续空闲期；绝对期限不续期；不为保活主动轮询 |
| 退出范围 | 仅撤销当前会话 | “所有设备退出”属于后续功能 |
| 提交去重窗口 | 从首次成功受理起至少保留 24 小时 | 窗口内重试不能重复创建；过期后不承诺识别历史请求 |
| 首版内容格式 | 纯文本 | 不解释为 HTML 或 Markdown，不自动加载外部媒体 |

“Unicode 码点”用于统一前后端字符计数，不等同于 UTF-8 字节数，也不保证一个显示出来的复合表情只占一个计数单位。页面应显示剩余可输入量并统一测试中文、换行和表情。

注册、登录、发帖及读取频率阈值需要根据部署容量在技术设计中配置。需求验收必须覆盖“达到阈值可按规则处理、超过阈值受限、等待后恢复”，不能以未确定线上数值为由省略限流能力。

## 5. 第一版功能需求

### FR-01 注册

**用户目标：** 获得可以发布留言的账号。

输入登录名、密码、确认密码，可选填写显示名称。前后端均做格式校验，服务端负责最终判断；密码与确认密码必须一致。登录名大小写差异不能创建两个账号，并发提交同名注册只能有一个成功。

注册成功后引导到登录界面并可带入登录名，不自动代替用户登录。注册失败需要给出可操作提示，保留非敏感输入；不向其他页面传播密码。

无邮箱、手机号、头像上传或身份认证流程。不能将“能注册”表述为已经具备找回密码功能。

验收关联：AC-01、AC-02。

### FR-02 登录与身份识别

**用户目标：** 用自己的身份发布和管理内容。

输入登录名与密码，成功后展示当前用户名称及退出入口；浏览器刷新后，在会话仍有效时能恢复身份。错误密码或不存在的账号使用统一的登录失败提示，不回显密码，也不返回内部账号详情。

允许多个设备分别登录，当前设备退出不自动撤销其他设备。服务端重启后是否保留未过期会话在技术设计中统一决定，P0 不要求跨重启保持登录；任何情况下都不能恢复已经撤销或过期的会话。该项与日常页面刷新保持登录是两个不同场景。

验收关联：AC-03、AC-04。

### FR-03 退出与会话失效

**用户目标：** 确保退出后不能再以该身份写入。

退出完成后，当前会话在服务端失效；仅清除页面上的用户信息不算退出。服务端过期或撤销会话后，后续写请求返回未登录结果。

用户在同一页面编辑时遇到登录过期，应保留当前页面内存中的草稿，登录后允许用户主动重试；不自动提交。切换账号后，不自动把上一账号的草稿带入新身份。

退出不回滚退出前已经成功提交的请求。与退出重叠的在途请求按服务端鉴权及受理时序处理，退出完成后开始的新请求必须失败。

验收关联：AC-04、AC-05、AC-23。

### FR-04 公开浏览与留言信息

**用户目标：** 未登录也能理解讨论内容、参与人和时间。

有效留言至少显示用户名称、正文、创建时间，并提供可查看的完整用户 ID。小屏可以使用“用户详情”展开 ID，但接口不得省略作者 ID。重复显示名称不能让用户身份混淆。

回复应明确标识直接回复对象；创建时间可以同时显示相对时间，但必须能查看带时区的完整时间。页面默认采用浏览器时区，服务端提供可明确解析的时间，不使用客户端提交的创建时间。

空留言板显示空状态和发布入口；已删除留言显示统一占位及原作者、原创建时间。读取不存在的留言应明确提示，不伪造空记录。

验收关联：AC-06、AC-07。

### FR-05 发布顶层留言

**用户目标：** 发起新的讨论。

未登录点击发布入口时引导登录。已登录用户输入正文并提交；空白、超长和超大请求被拒绝。服务端决定作者、留言 ID 和创建时间，忽略或拒绝客户端试图指定作者、角色、时间等受保护字段的行为。

提交时显示处理中并减少重复点击；保存成功后清空本次编辑内容并反馈成功。只有当新节点属于当前已加载的排序范围时，才把它直接合并进列表；否则提示已发布以及需要刷新或继续加载，不能为展示新记录而破坏排序或漏掉中间记录。

未明确收到成功结果时，按 FR-12 处理重试。失败不清空草稿。

验收关联：AC-08、AC-09、AC-22、AC-23。

### FR-06 任意层级回复

**用户目标：** 直接回应某一条具体留言，而不是只能回应整场讨论。

每条 active 留言都提供回复入口，包括自己的留言和具有已删除祖先的有效留言。编辑时显示正在回复的用户和目标留言信息，用户可以取消回复。

服务端必须确认父节点存在且允许回复，确定真实父节点及所属根；不能信任客户端自报根关系。新节点只归属于一个直接父节点。父关系创建后不通过普通编辑或页面布局变化进行调整。

不存在的父节点返回“目标留言不存在”；已删除父节点返回“该留言已删除，无法继续回复”，保留草稿，不自动改成回复它的父节点。

无限层级是数据和操作能力要求。业务不应在第 3、10 或 1000 层等位置人为停止回复；每次操作仍必须遵守请求大小、时间和数量预算。

验收关联：AC-10、AC-11、AC-12、AC-27。

### FR-07 树形展示、折叠与深层导航

**用户目标：** 看清谁在回复谁，并控制页面复杂度。

按照真实父子关系展示分支；父节点在自己的后代之前，同级节点遵守 FR-09。可以独立展开、收起某个分支，收起不改变数据关系，也不影响其他分支。

深层展示不能无限向右挤压正文。允许缩进封顶和聚焦子树，但仍要显示直接回复对象，提供查看父节点和返回上一浏览位置的操作。聚焦只是浏览视角变化，不能把非根节点伪装为新的数据根。

当前浏览路径可以按段查看，不能要求一次返回所有祖先正文。当前实现支持通过 `?focus=<留言ID>` 分享深层聚焦地址，祖先上下文仍然有数量上限。

验收关联：AC-10、AC-13、AC-27、AC-28。

### FR-08 顶层及分支分页

**用户目标：** 留言再多也能逐步加载，并在失败后继续。

首次打开只请求一页顶层留言。展开 A，只请求 A 的直接回复，不连带加载 B、C 的全部后代。每个分支有自己的“加载更多”、加载中、失败和结束状态。

重复展开已加载分支可复用有效数据；合并结果按留言 ID 去重。折叠后再次展开仍保持正确关系，必要时允许重新查询。

请求必须限定返回条数；不能通过极大 limit、空参数或错误游标触发全量查询。游标应与排序方向、父节点范围匹配，混用和非法游标明确失败。第一版不要求页码跳转，也不要求精确的总评论数或全部后代数。

数据尚未加载时不能显示为“没有回复”；加载失败时不能显示为“已加载完”。无更多数据时停止重复请求。

验收关联：AC-14、AC-15、AC-16、AC-26。

### FR-09 时间排序

**用户目标：** 按新旧顺序浏览，同时保留对话结构。

根列表提供“最新优先／最早优先”切换；每个父节点的直接回复固定为最早优先。时间相同时，按唯一留言 ID 做稳定的并列裁决；这不宣称代表事务提交先后。

切换根排序后应重置对应列表的游标和加载范围，保留尚未提交的草稿并提示用户仍在回复的对象。不能用旧方向游标继续读取新顺序。

分页采用实时数据语义，不承诺多个请求共享一个历史快照。并发新增可能出现在已浏览范围之前，需要刷新才能看到；页面不得承诺当前已加载的是全量最新数据。

验收关联：AC-17、AC-18、AC-22。

### FR-10 删除自己的留言

**用户目标：** 撤回自己发布的正文，同时保留其他人的讨论。

只有作者能执行普通删除。删除前明确提示“删除本条内容，已有回复将保留”，用户可以取消；确认后才发送请求。服务端校验所有权。

成功后正文被清空，状态变为 deleted，显示“该留言已删除”；原作者、原创建时间、留言 ID、父／根关系及所有后代保留。根、中间节点和叶子使用相同规则。

删除完成后的新读取不得返回旧正文；当前操作页面也要清除旧正文缓存。其他已经打开的页面不要求实时推送更新，其后续刷新或重新获取必须得到占位。该规则不能撤回其他人此前已读取或截图的内容。

作者重复删除同一节点视为成功，不重复改变子回复。第一版没有“恢复原文”功能；已删除对象仍需检查身份和所有权，不能因为操作幂等就跳过权限校验。

验收关联：AC-19、AC-20、AC-21。

### FR-11 删除与回复并发

**用户目标：** 同时操作时不丢失已成功提交的回复，也不向已删除目标新建回复。

对同一目标 B，服务端必须产生符合以下规则的确定结果：

- 回复在删除之前被成功受理并提交：新回复保留，B 随后成为删除占位。
- 删除已提交后才检查并受理新回复：拒绝新建，保留客户端草稿。
- 任一操作失败回滚：不留下半条回复、错误关系或假成功状态。

具体事务、锁和重试策略由技术设计确定，但仅在事务外检查一次父节点存在不满足要求。数据库冲突或锁等待超时应有可理解的失败结果，不能无限等待或无限重试。

验收关联：AC-24、AC-25。

### FR-12 提交去重与结果不明时的重试

**用户目标：** 网络超时或重复点击不会发布两条相同操作。

一次用户提交具有稳定的请求标识，范围由当前用户身份隔离；同一用户、同一请求标识及同一有效负载在去重窗口内只能产生一条留言。并发请求也必须满足这一点。

同一标识对应不同正文或不同回复对象时，返回冲突，不覆盖已保存的留言。重试已完成的请求应返回原结果的当前可见状态，不再次执行创建。

特别地：C 已创建成功但响应丢失，随后父 B 被删除，重试创建 C 应确认原 C 的结果，而不是误判为一次新的无效回复。如果 C 自己随后已删除，重试返回其删除状态，不能恢复原文。

页面只能重试当前用户主动发起的操作，不把自动重试当作再次发帖；修改负载属于新的提交意图，不能复用旧标识。去重记录与业务结果必须保持一致。

验收关联：AC-22、AC-25。

### FR-13 异常反馈与草稿

**用户目标：** 明白当前操作是否成功，能继续完成输入。

至少区分：输入不合法、未登录、无权限、目标不存在、父节点已删、请求标识冲突、请求过大、频率受限、网络失败和服务异常。页面显示可理解的中文提示，不展示堆栈、SQL 或敏感数据。

首屏失败提供重试；某个分支失败只影响该分支；删除失败不能先把留言永久移除。请求处理中、成功、失败、空列表和没有更多数据需要明确区分。

草稿保证限于当前页面会话内：网络失败、服务端拒绝、登录过期或排序切换不能无提示清空。刷新、关闭页面和跨设备恢复草稿不属于第一版；主动退出或切换身份清除对应内存草稿，避免误用身份。

验收关联：AC-05、AC-15、AC-18、AC-23。

### FR-14 响应式与键盘可用性

**用户目标：** 在手机和桌面上都能完成核心操作。

至少覆盖 360px 手机视口和 1280px 桌面视口。长单词、长 ID 和连续文本不能把主要内容区撑出横向滚动。深层分支遵循 FR-07 的导航规则。

注册、登录、发布、回复、删除确认和加载更多均可用键盘完成；按钮、输入框具有可识别名称；错误信息与对应输入关联，焦点状态可见。

正文输入中 Enter 默认换行；提交采用明确按钮，若增加快捷键必须提示。不能仅凭颜色表达已删除、错误或选中状态。

验收关联：AC-28。

## 6. 数据需求与一致性

本节描述业务必须保存和保证的信息，不规定实际 SQL 类型、表名或 ORM 对象。

### 6.1 核心实体

| 实体 | 必要信息 | 业务约束 |
| --- | --- | --- |
| 用户 | 稳定用户 ID、唯一登录名、显示名称、密码验证信息、创建时间 | 显示名称允许重名；所有权依赖 ID；公共接口不返回密码验证信息 |
| 留言 | 稳定留言 ID、用户 ID、正文、创建时间、直接父 ID、根 ID、状态、删除时间 | 根的父为空；所有回复都有真实直接父；所属根一致；创建后不修改作者与创建时间 |
| 登录会话 | 当前身份、有效期、撤销信息 | 服务端决定有效性；退出及过期后不能继续使用 |
| 提交去重记录 | 用户、请求标识、有效负载摘要、结果引用、保留期限 | 同一用户及标识唯一；重试关联原结果；不另存可被读回的已删正文副本 |

“用户名称”可以由用户关联查询得到，不要求每条留言重复保存一份名称。第一版不提供改名，未来开放改名时再确定历史显示规则。

### 6.2 必须保持的不变量

| 编号 | 不变量 |
| --- | --- |
| DR-01 | 不存在指向不存在用户的有效作者关联 |
| DR-02 | 非根留言的直接父必须存在；父节点被内容删除不破坏引用 |
| DR-03 | 根节点的根 ID 为自身；后代与其直接父共享同一个根 ID |
| DR-04 | 不允许自己作为父，也不允许父链形成循环；不能只靠前端阻止 |
| DR-05 | 用户操作不能把 C 的父从 B 改为 A；布局缩进不影响数据 |
| DR-06 | active 正文满足长度和非空白要求；deleted 正文为空，不再返回旧原文 |
| DR-07 | 删除不修改原创建时间；删除时间与创建时间分别表示不同事件 |
| DR-08 | 公共响应至少包含作者 ID、作者名称、正文或删除状态、创建时间及必要父子关系 |
| DR-09 | 前后端 ID 使用不会丢失精度的表示；时间带明确时区语义；排序键保持稳定 |
| DR-10 | 创建结果和对应去重记录一致；失败不能留下可误报成功的去重结果 |

管理员、审核状态、点赞关系、通知等实体不提前计入 P0 数据范围。图片附件已作为本轮扩展实体单独建表；其他扩展字段和状态仍不能视为已实现功能。

### 6.3 状态规则

留言状态只允许从 active 转为 deleted，重复删除保持 deleted。P0 不提供 deleted 转回 active。

网络超时不改变留言业务状态，页面应标记结果待确认；加载失败也不能把留言标为 deleted。未来加入 waiting、hidden 等状态时，需要重新定义其读取权限、回复资格和后代展示规则。

## 7. 非功能需求

### NFR-01 查询范围与请求预算

根列表和直接回复列表都必须使用有界分页，单请求返回条数遵守第 4 节默认参数。请求 20 条直接回复时，不能先加载完整讨论再在内存中截取。

不得为本页每条留言逐一发起作者查询、回复统计查询，形成随着页大小线性增长的数据库往返。业务读取 SQL 次数目标不超过 3 次／列表请求；会话鉴权读取单独统计。数据库内部关联、索引探测的成本仍需观察，SQL 次数少不等于查询代价低。

关键查询应有与父节点过滤和时间排序相匹配的索引设计，并提供实际 PostgreSQL 执行计划。小表被优化器选择全表扫描不直接判为失败；大数据量下必须解释扫描量与返回量是否合理。

### NFR-02 深度、宽度与渲染容量

数据层不设置固定最大回复层数；页面单次响应、可见内容和祖先上下文均有数量边界。不能依赖与完整链深度等长的函数调用栈或无限嵌套 JSON。

长列表采用窗口化、分支聚焦或其他可证明有界的展示方式。正常浏览同时挂载的留言卡片建议预算不超过 200 个；如果采用不同预算，应在技术设计中说明，并用同等规模测试证明页面仍可交互。第一版需要覆盖 10000 层单链和 50000 个直接子节点两类极端分布。

客户端缓存同样需要容量或淘汰策略，不能仅限制 DOM，却无限保存所有访问过的分支正文。具体缓存数量在前端设计中确定。

### NFR-03 安全与访问控制

必须由服务端校验身份、所有权、输入长度和受保护字段；查询使用参数绑定，排序字段由固定允许值映射。

密码使用专门的不可逆密码哈希方案，通过成熟库验证；不得明文保存，也不得把普通摘要直接当密码存储方案。认证、会话和授权使用已确定的 Spring Security 集成，具体参数在技术设计中锁定。

公网部署使用 HTTPS；会话 Cookie 采用合理的 HttpOnly、Secure 和 SameSite 设置，写请求具有 CSRF 防护。正文和名称按纯文本安全显示，恶意标签和脚本不得执行。

注册、登录、发布及读取具有限流机制，并区分账号与来源风险；请求大小、分页参数和内部等待有上限。达到限流返回明确状态及可重试提示，不能无限占用连接。反向代理来源信息必须按可信代理配置处理。

### NFR-04 隐私与删除后的数据处理

公共响应不得提供密码哈希、会话凭据、邮箱、原始 IP、用户代理或其他与公开阅读无关的信息。初版注册不要求邮箱与手机号。

日志默认不记录密码、凭据、正文全文和完整含敏感参数的请求。提交去重结果不得作为旁路重新暴露已删除正文。

删除完成后，后续新读取不能得到旧正文；如果未来引入缓存、搜索、邮件和消息副本，要追加对应清理及可见性规则。数据库备份可能含历史正文，必须制定保留及恢复后删除处理规则，不能宣称普通内容删除自动擦除所有备份。

### NFR-05 事务与故障一致性

注册唯一性、创建留言、提交去重以及删除状态更新均应有明确原子性。并发成功与失败须满足 FR-11、FR-12 及 DR-01 至 DR-10。

数据库断开、进程异常、锁超时或请求中断时，不得对未提交操作报告成功。对可重试错误采用有界重试；无法确认结果时使用原请求标识确认，不能无限重发新请求。

### NFR-06 可观察性

失败操作有可关联的请求标识，便于区分输入问题、鉴权失败、数据库异常和内部错误。日志及指标能够观察接口延迟、错误比例、数据库调用次数、超时及限流情况，不通过记录正文获取这些信息。

对外错误不暴露内部堆栈。后续测试报告应保留环境、参数、数据分布和实际结果，而不只写“测试通过”。

### NFR-07 可维护性与可复现性

前端展示、后端鉴权、留言业务、数据访问、数据库迁移、验证材料和部署配置职责分离。环境相关配置与凭据外置，依赖版本锁定。

数据库结构变化通过版本化迁移管理。业务逻辑不能散落在前端显示条件或数据库访问代码中，使权限和删除规则无法集中检查。

最终交付需提供安装运行说明、配置项说明、数据库迁移说明和实际验证结果。业务测试针对权限、关系、分页与并发行为，不以大量重复实现逻辑的测试代替验收。

### NFR-08 性能验收方法

性能验收分为硬性结构要求和待环境确定的延迟目标。

**硬性要求：** NFR-01 的分页与查询预算、NFR-02 的深宽树可用性、FR-11 的并发规则及 FR-12 的去重规则必须通过。

**候选延迟目标：** 常规列表 API 的 p95 不超过 300ms。p95 指至少 95% 的测量请求不超过该耗时；这是待目标环境确认的验收指标，不是测量结果。

建议基准负载：100000 条混合层级留言，50 个并发读取客户端与 10 个并发写入客户端，预热后持续运行至少 5 分钟；另对宽树、深链分别验证。延迟统计区分正常请求、限流和业务拒绝，不允许用大量快速拒绝掩盖成功请求变慢。

压测前记录 CPU、内存、PostgreSQL 与 Java 版本、数据库与应用是否同机、索引、连接池、正文大小、冷／热缓存、测试端网络和限流配置。若环境或负载更改，应先重新明确正式指标，再执行和评价；不能测试后随意修改阈值来宣称达标。

## 8. 扩展需求与发布边界

下列需求承接前期调研，均不默认计入 P0 开发任务。公网前置项属于真实运营的必要补充；它们的完整流程需在对应迭代补充详细需求。

| 编号 | 优先级 | 功能与价值 | 关键规则和风险 | 是否公网前置 |
| --- | --- | --- | --- | --- |
| E-01 | P1 | 管理员治理、账号封禁：能处理恶意内容和持续刷屏 | 管理身份不能自助注册获得；审核管理操作留审计；封禁后撤销相关会话。普通内容删除与管理隐藏的语义分开 | 是，至少具备基本移除违规正文与封禁能力 |
| E-02 | P1 | 账号恢复：忘记密码后能重新控制账号 | 必须验证账号控制权；不能仅凭公开用户名重置；重置 token 一次性、限时且只保存哈希；详细规则见 `auth-registration-requirements.md` | 是，需要配置 SMTP 并完成实际收信验收 |
| E-03 | P1 | 备份恢复：数据库故障和误操作后可恢复 | 明确保留期、可接受数据损失及恢复时间；实际恢复演练；避免恢复后已删正文重新公开 | 是 |
| E-04 | P1 | 我的留言、深链接：快速找到自己或指定节点的讨论 | 深层聚焦地址和有限祖先上下文已实现；个人列表、完整通知和长期链接治理仍需单独验收 | 部分 |
| E-05 | P1 | 举报与审核：建立处理争议内容的入口 | 防重复及恶意举报；定义待审父节点与后代的可见性；审核结果不得使关系悬空 | 否，可先使用基本管理能力 |
| E-06 | P1 | 回复通知：知道有人回复自己 | 去重、不向无权查看者发送内容；不因重试重复通知；避免发送已删除正文 | 否 |
| E-07 | P2 | 编辑、点赞、搜索、Markdown：改善表达和内容查找 | 编辑需考虑历史上下文；点赞唯一性与刷赞；搜索删除同步；Markdown 解析后净化 | 否 |
| E-08 | P2 | 图片附件、第三方登录、实时更新：丰富交互 | 图片附件已按独立容量、类型和本地生命周期规则实现；对象存储、外部账号绑定及推送容量仍需独立设计 | 图片附件已实现，其余否 |

P0 不实现“作者一键删除整棵子树”。若以后引入管理员子树治理，必须明确权限、删除范围、冻结或并发协调、任务失败恢复及审计；不能复用普通作者删除接口就宣称满足要求。

## 9. 页面与交互需求

| 页面／区域 | 必要内容 | 必须处理的状态 |
| --- | --- | --- |
| 留言板主页 | 当前身份或登录入口、顶层发布框、时间排序、留言列表、加载更多 | 初次加载、空板、失败、部分已加载、无更多 |
| 留言卡片 | 作者名称、可查看的用户 ID、正文或删除占位、创建时间、回复目标、展开／收起、回复入口、作者删除入口 | active、deleted、没有子节点、子节点尚未加载 |
| 分支区域 | 直接回复列表、独立的加载更多、父节点关系和深层聚焦导航 | 加载中、成功、失败、已结束、折叠 |
| 注册页面／弹层 | 登录名、可选显示名称、密码、确认密码、规则说明 | 输入错误、重名、受限、成功引导 |
| 登录页面／弹层 | 登录名、密码、提交入口 | 处理中、失败、受限、成功恢复当前页面操作位置 |
| 回复编辑区域 | 回复对象、正文输入、取消、提交、长度反馈 | 编辑中、提交中、失败、登录过期、目标已删除 |
| 删除确认弹层 | 说明删除本条正文且保留子回复，确认／取消 | 确认中、失败、成功替换占位 |

“未加载子回复”和“无子回复”是不同状态；提示文案不得把二者混为一谈。第一版可以使用“展开回复”，不要求显示精确数量。

当服务端确认发布成功但新记录不属于当前已加载范围时，展示成功提示和本次发布结果摘要，不强制把它插入错误位置；用户可按当前排序继续加载或刷新。刷新和重新请求以服务端最新状态为准，已删正文不能从临时结果摘要重新恢复。
