# 留言板调研与设计建议

调研日期：2026-10-20。阶段：需求分析与方案设计。本文未实现应用代码，未部署或运行被调研项目，也未进行性能测试。

后续记录：用户已选择 Vue 3＋TypeScript＋Vite，Java 21＋Spring Boot＋Spring Security＋MyBatis，PostgreSQL。当前功能范围、建议默认值及验收要求见[需求分析说明书](./requirements.md)。下文保留调研时的候选方案与历史表述，不把“当时尚未选型”视为当前状态。

建议第一版实现一个独立的、登录后可发布的单留言板：真实保存任意层级的父子关系；顶层留言和每个节点的直接回复分别分页；作者删除自己的留言后保留结构占位及其他人的回复。

“无限层级”在本文中的含义是：业务模型不预设两层、三层等固定回复上限，任意有效留言都可以继续被回复。服务器、数据库和浏览器仍然受资源限制，因此每次查询、响应和渲染必须有界，不能承诺一次加载任意大的整棵树。

## 3. 源码里最值得借鉴和警惕的地方

### 3.1 Remark42：树形关系明确，但分页不等于响应大小严格受控

**源码确认：** `MakeTree` 根据 `ParentID` 建树；`proc` 递归处理子节点。删除节点没有可见后代时会被清理出展示树，有可见后代时则可以保留结构。`EditComment` 中存在使用 `SoftDelete` 的删除路径，但删除权限和时间窗口还受其他逻辑约束。

源码：[建树与删除节点展示处理](https://github.com/umputun/remark42/blob/4de6532c0a4e6aa5c09b3800aae52fce3a8e1c50/backend/app/store/service/tree.go#L34)、[软删除路径](https://github.com/umputun/remark42/blob/4de6532c0a4e6aa5c09b3800aae52fce3a8e1c50/backend/app/store/service/service.go#L473)。

**风险推断：** 所读 `proc` 为每个节点过滤传入的评论列表；对 N 个节点反复扫描时，组树部分最坏可能接近 O(N²)，这里没有计入排序等额外开销。其 `limit` 以保留完整顶层讨论为前提，第一棵讨论树本身很大时可以超过 limit。

这不构成“Remark42 实测性能差”的结论；它说明我们不能直接把这段策略当作“大讨论严格有界加载”的方案。我们只对已加载的有限节点建立映射，并给每个节点的直接回复独立分页。

源码：[逐节点过滤](https://github.com/umputun/remark42/blob/4de6532c0a4e6aa5c09b3800aae52fce3a8e1c50/backend/app/store/service/tree.go#L73)、[保留整棵讨论的限制逻辑](https://github.com/umputun/remark42/blob/4de6532c0a4e6aa5c09b3800aae52fce3a8e1c50/backend/app/store/service/tree.go#L163)。

### 3.2 Waline：区分直接父评论与根评论很有用

**文档及源码确认：** `pid` 表示直接回复对象，`rid` 表示所在讨论的根评论。列表先分页查询根，再用根 ID 集合批量查回复，避免在应用层为每条根评论分别发起一次回复查询。返回时把同根回复放入根的 `children`，再用 `pid` 找到被回复者。

源码：[根分页、批量取回复与组装](https://github.com/walinejs/waline/blob/05327db6fffcbc9afa928e843f36693826eaeb44/packages/core/src/handlers/comment.ts#L44)、[客户端展示](https://github.com/walinejs/waline/blob/05327db6fffcbc9afa928e843f36693826eaeb44/packages/client/src/components/CommentCard.vue#L168)。

**风险推断：** 根分页并没有对一个根下返回的回复数单独限量。一个根下有几万条回复时，批量查询仍可能很重。我们保留父／根字段的思想，但正常浏览以 `parent_id` 查询直接子节点，不按 `root_id` 全量取回后代。

删除也值得单独研究：所读 `remove` 使用“目标 ID、直接父 ID、根 ID 任意一个等于目标 ID”的条件删除。它并不是对任意节点执行递归后代遍历。

假设存在 A → B → C → D，D 的 `pid=C`、`rid=A`，删除中间节点 B 时，上述条件可以覆盖 B、C，但没有直接覆盖 D。**这是基于该函数的静态推断，未运行复现，也未排除具体存储适配器中的附加行为。** 它足以说明：我们不能把“按 pid/rid 删除”的逻辑不加验证地移植为通用子树删除。

源码：[删除条件与所有权校验](https://github.com/walinejs/waline/blob/05327db6fffcbc9afa928e843f36693826eaeb44/packages/core/src/handlers/comment.ts#L397)。

### 3.3 Isso：“能回复回复”也可能仍然只有两层关系

**源码确认：** `Comments.add` 内部 `_find` 会沿父链上溯，并把新评论的父节点替换为找到的顶层节点。因此不能仅凭页面存在“回复”按钮判断它保存了无限层级。

**源码确认：** 删除有子回复的评论时，Isso 清空正文、标记软删除，并清理作者等部分展示字段；没有子回复时可以直接删除。本文不把它等同于“所有个人数据均被清除”，因为所读实际字段更新并不覆盖全部字段。

源码：[父节点归并](https://github.com/isso-comments/isso/blob/413d447a46437d0e9ccf206c8525119355e291d4/isso/db/comments.py#L75)、[删除实现](https://github.com/isso-comments/isso/blob/413d447a46437d0e9ccf206c8525119355e291d4/isso/db/comments.py#L333)。

它的排序规则也有参考价值：官方文档允许顶层按最新、最早或票数排序，并说明回复使用最早优先。我们的第一版可以采用“顶层新到旧、同父回复旧到新”的默认方式。[Isso 客户端配置](https://isso-comments.de/docs/reference/client-config/)

### 3.4 giscus、Talkyard：参考产品取舍，避免把未确认内容写成承诺

giscus 的 `IComment` 有 `replies: IReply[]`，`IReply` 本身没有递归的 replies 字段；本次读取的查询也只展开一层 replies。这足以确认该路径不是我们需要的递归树契约。查询中的 `last: 100` 只是该次查询的请求参数，不能据此断言整个产品最多只能保存 100 条回复。

源码：[类型定义](https://github.com/giscus/giscus/blob/3d6430237108ca4ee3eb6a1a20595201c09c72d5/lib/types/adapter.ts#L27)、[讨论查询](https://github.com/giscus/giscus/blob/3d6430237108ca4ee3eb6a1a20595201c09c72d5/services/github/getDiscussion.ts#L23)。

Talkyard 的“跳回父评论”“快速寻找最近回复”能改善长讨论阅读。但它的无限层级存储、删除规则和查询成本本次未审计，不能直接认定满足全部要求。giscus、Talkyard 的删除传播范围也没有在本次调研中完成确认。

## 5. 用一个具体场景确定父子关系

假设有以下对话，箭头表示“直接回复”：

```text
A：这个周末去哪里？
├─ B：可以去公园。             B 回复 A
│  └─ C：哪个公园？             C 回复 B
│     └─ D：市中心的那个。       D 回复 C
└─ E：我想去图书馆。           E 回复 A
```

数据库记录：

| id | parent_id | root_id | 含义 |
| --- | --- | --- | --- |
| A | 空 | A | 顶层留言 |
| B | A | A | A 的直接子节点 |
| C | B | A | B 的直接子节点 |
| D | C | A | C 的直接子节点 |
| E | A | A | A 的另一个直接子节点 |

`parent_id` 回答“这条直接回复谁”；`root_id` 回答“它属于哪一场讨论”。知道 root_id 不能替代直接父子关系，也不能直接识别“以 B 为起点的全部后代”。

创建 D 时，浏览器只提交正文、父节点 C 的 ID 和本次提交标识。作者、根 ID、创建时间都由服务端计算，不能信任浏览器传来的这些字段。

删除 B 后：

```text
A：这个周末去哪里？
├─ B：[该留言已删除]
│  └─ C：哪个公园？
│     └─ D：市中心的那个。
└─ E：我想去图书馆。
```

C 仍然回复 B，不能自动改成回复 A，否则对话语义被改变。用户也不应仅因为自己发布了 B，就获得删除 C、D 的权限。

## 6. 树形存储方案比较与推荐

以下比较是针对本项目读写模式的设计分析，不是对上述产品做的数据库性能测试。

| 方案 | 保存方式 | 优点 | 成本与风险 | 当前建议 |
| --- | --- | --- | --- | --- |
| 邻接表 | 每条记录存直接父 ID | 插入简单，直接子节点查询自然，适合持续追加 | 查完整子树需递归查询；必须管理孤儿和循环 | 推荐作为基本模型 |
| 邻接表＋根 ID | 增加所属根节点 | 保留直接关系，便于整场讨论定位、管理和导出 | 冗余字段必须由服务端维护一致；按根取全部后代仍可能很大 | 推荐第一版 |
| 物化路径 | 保存类似 A/B/C 的祖先路径 | 祖先、子树查询直观，可结合适当索引 | 深链路径变长，迁移节点需更新后代；不能用有限字符串长度暗中限制层级 | 暂不采用 |
| 闭包表 | 单独保存每对祖先与后代及距离 | 祖先／后代查询方便 | 新增节点需要插入祖先关系；长度 N 的单链关系数可达 N(N+1)/2 | 对当前简单高追加场景不划算 |
| 嵌套集 | 每个节点保存左右边界 | 读取静态整棵子树方便 | 频繁插入可能修改大量边界，并发写复杂 | 不适合第一版 |

建议数据库优先考虑 PostgreSQL：它提供事务、外键、复合索引和递归 CTE，可以覆盖当前需要。后端语言和前端框架尚未由需求指定，不应因参考项目使用 Go、Python 或 Node.js 就直接锁定技术栈。

正常浏览只查直接子节点，不需要每次递归整棵树。递归 CTE 留给有边界的祖先上下文、管理、修复和导出；需要显式处理循环与执行预算。PostgreSQL 官方说明递归 CTE 适合树形关系，但在外层写 LIMIT 并不能普遍保证递归工作量被限制，尤其外层排序或连接时。[PostgreSQL 递归查询与循环检测](https://www.postgresql.org/docs/current/queries-with.html)

## 7. 建议的数据模型与约束

当前先按“只有一个公共留言板”设计；多板块、多租户不进入第一版。以后增加板块时，需要为父、根关系增加同板块约束。

| 实体 | 主要字段 | 关键约束 |
| --- | --- | --- |
| 用户 | ID、规范化登录名、显示名称、密码哈希、账号状态、创建时间 | 登录名唯一；ID 不随名称变化；哈希不出现在公共响应 |
| 会话 | 会话标识摘要、用户 ID、过期时间、撤销状态 | 原始随机标识放安全 Cookie；服务端可撤销，过期后无效 |
| 留言 | ID、parent_id、root_id、user_id、正文、状态、创建时间、删除时间 | ID 唯一；作者及父／根引用有效；根的 parent 为空且 root 为自身 |
| 提交去重记录 | 用户 ID、请求标识、请求摘要、结果留言 ID、过期时间 | 用户＋请求标识唯一；同标识不同请求应拒绝；保留期需要明确 |

补充规则：

1. 普通留言状态先只需要 `active` 和 `deleted`。审核、管理员隐藏作为后续独立扩展，避免第一版出现没有定义的状态组合。
2. 已删除留言清空正文并保留结构。第一版保留所有删除占位，包括叶子节点；这样查询规则明确。自动清理空分支可后续加入，届时需要解决分页及并发影响。
3. 第一版账号不支持改名；公共留言响应通过用户关联获得名称。以后允许改名时，需要决定旧留言显示当前名称还是发布时快照。
4. `parent_id` 和 `root_id` 创建后不可通过普通接口修改。每次创建只允许引用已存在的有效父节点；在没有移动／导入路径时，这能从构造方式上避免形成循环。
5. 父 ID 外键使用阻止误删关系的策略，不把数据库 `ON DELETE CASCADE` 当成默认的用户删除操作。外键本身不能阻止所有循环，迁移和导入仍要检查。
6. 根 ID 从父节点继承，不能使用客户端传入值。根／父字段的跨行一致性需要写入服务和校验任务保障；普通外键只证明“引用存在”，不证明“属于正确的根”。
7. 不要求保存 depth；需要时从已知父层级推导。若保存，它只是冗余展示数据，不应成为设置固定最大回复深度的依据。
8. ID 在 API 中统一按字符串传输，避免将来使用大整数主键时被 JavaScript 精度截断。
9. 时间由服务端／数据库产生，采用带时区的时间类型，响应使用带时区的 ISO 8601 格式；界面按用户时区展示。
10. 日志默认不记录密码、会话原文和留言全文；删除正文后，需要检查后续引入的缓存、搜索索引和通知是否仍能显示旧内容。

建议索引：

| 索引方向 | 用途 |
| --- | --- |
| 规范化登录名唯一索引 | 注册重名校验与登录查询 |
| 顶层留言的 `(created_at, id)` 部分索引，条件为 parent_id 为空 | 顶层时间排序及游标分页 |
| `(parent_id, created_at, id)` | 直接回复查询；同时支持检查是否存在子节点 |
| `root_id` | 整场讨论定位、后续管理和导出；不用于首屏全量拉取 |
| `(user_id, created_at, id)` | “我的留言”上线时再增加 |

是否实际使用索引、是否发生额外排序，需要后续用真实查询计划验证。匹配排序的 B-tree 索引与 LIMIT 组合有助于只读取所需的一小批行，但不能据此承诺所有查询都是固定耗时。[PostgreSQL 索引与排序](https://www.postgresql.org/docs/current/indexes-ordering.html)

## 8. 查询和前端展示如何做到有界

### 8.1 首屏只取顶层，展开只取直接回复

建议初始参数：顶层每页 20 条；直接回复每页 20 条；服务端允许的单页最大值为 100。数值是设计初值，后续可以根据实际体验调整。

完整流程：

1. 页面打开，只请求 20 条顶层留言，附带“是否有直接回复”和下一页游标。
2. 用户展开 A，只请求 parent_id=A 的前 20 条直接回复，例如 B、E。不会自动获取 C、D。
3. 用户展开 B，再请求 parent_id=B 的直接回复，此时才获得 C。
4. 任意节点都支持自己的“加载更多”，拥有独立游标、加载状态和错误状态。
5. 作者名称通过 JOIN 或对本页用户 ID 的一次批量查询获取，避免每条留言再请求一次用户表。

这将一次请求的工作量与当前页大小关联。某条讨论达到十万条回复时，首次展开仍只需要一页直接回复。实际耗时仍受索引、数据分布、缓存和并发影响。

第一版先不在首页为所有根预取回复。以后需要“每个根预览两条”时，应使用每个父节点分别限量的批量查询方案；不能简单查询所有 root_id 对应的后代，也不能只给整个集合加一个全局 LIMIT。

`has_children` 可以通过索引支持的 EXISTS 子查询在列表 SQL 中一起取得，不在应用层循环查询，也无需每次精确统计整棵子树。第一版不显示精确“全部后代数量”，以减少热点计数维护和大范围统计。

### 8.2 时间排序的语义要写清楚

树形展示的“按时间排序”是指：

- 顶层之间按时间排序，默认最新在前，可切换最早在前。
- 同一个父节点下的直接回复按时间排序，默认最早在前；接口预留同样的顺序参数。
- 父节点总是在其子树之前展示，不把整块留言板打散成全局时间线。

例如 E 比 D 早，也不要求 E 穿插进 B → C → D 的分支。全局时间线和树形视图是两种不同产品模式，后续若增加“最近回复”，应该单独提供入口。

排序用 `(created_at, id)`，而不是只用 created_at。相同时间的记录由唯一 ID 确定顺序；ID 的顺序只是稳定的并列裁决，不宣称代表事务提交先后。

游标包含排序方向、父节点范围和最后一条记录的时间／ID，服务端验证它与当前请求匹配。改变排序后重新加载，不能沿用旧游标。

相比深 OFFSET，游标无需跳过前面大量行；PostgreSQL 文档指出 OFFSET 跳过的行仍需要由服务端计算，并要求 LIMIT 分页采用确定排序。[PostgreSQL LIMIT 与 OFFSET](https://www.postgresql.org/docs/current/queries-limit.html)

游标并不等于跨多次请求的数据库快照。并发新增可能出现在当前游标之前，正在浏览的用户需要刷新才能看到；极端提交时序下也不能承诺一轮浏览精确遍历某个历史瞬间的全部记录。第一版采用实时列表语义，不做长事务维持跨页快照。

### 8.3 不返回无限嵌套的 JSON，也不无限加深 DOM

每个列表响应返回本页的扁平节点、真实 parent_id、root_id、has_children、has_more 和 next_cursor；不把整棵树序列化成层层 children 的大 JSON。

前端用“节点 ID → 节点”和“父节点 ID → 已加载子节点 ID 列表”保存状态。对加载的节点建立映射为 O(M)，M 为已加载节点数；排序若在前端重新做，仍有单独的排序成本。

使用显式栈进行迭代式树遍历，生成当前可见行，避免函数调用栈跟着回复深度增长。可见行也采用窗口化或分支聚焦，保证不会一次渲染上万层 DOM；折叠后允许淘汰旧分支页缓存。

桌面和手机的视觉缩进可以分别限制为约 5 层和 3 层，这是布局规则。超过后仍保留真实 parent_id，显示“回复某用户”、连接关系和进入该分支的入口，可通过聚焦子树继续阅读。不能因为停止缩进，就在数据层把 C、D 都改成 A 的直接回复。

祖先上下文也要分段：不能为了定位第 10000 层节点，一次返回它的全部祖先正文。后续深链接接口可以每次取最多 20 个祖先，返回继续向上的位置。

## 9. 删除策略和并发边界

### 9.1 三种可选产品规则

| 规则 | 删除 B 后 C、D 的结果 | 适用情形 | 主要问题 |
| --- | --- | --- | --- |
| 清空 B 内容，保留占位 | 原样保留，仍能沿原关系阅读 | 普通用户删除自己的内容 | 会有空占位；必须确保旧正文不从其他读路径泄露 |
| 删除整棵 B 子树 | C、D 一并删除 | 管理员处理整段违规讨论 | 作者可能误删他人内容；遍历、并发和长事务成本高 |
| 把 B 的子节点提升到 A | C 被改成回复 A | 明确允许重组讨论的产品 | 改变回复含义，引用／通知／排序容易产生矛盾 |

**第一版选择第一种。** 它已经处理了子回复：保留子回复和父节点结构，既不产生悬空引用，也不会让普通作者删除其他人的内容。

普通删除保留用户 ID、时间和关系，清空正文，响应显示删除占位。它不是注销账号或删除全部个人数据的功能。以后加入账号注销，应另行确定身份匿名化和备份处置规则。

删除操作需要一个明确提示：“删除本条内容，已有回复将保留。”同一作者重复删除同一记录返回成功，避免网络重试造成异常状态。

### 9.2 删除 B 与回复 B 同时发生

不能只在事务外执行“查到 B 存在”，然后直接插入。

推荐两个操作都使用同一行锁协议：

1. 回复事务读取并锁定 B，检查它是否仍 active。
2. 若有效，则插入 C，并提交事务。
3. 删除事务也锁定 B，再完成所有权校验和正文清空。

如果回复先获得锁并提交，随后删除 B，C 保留在占位下；如果删除先提交，回复事务看到 deleted，返回 `409 PARENT_DELETED`。前端保留用户草稿，提示更换回复对象。

删除 B 不禁止继续回复仍有效的 C：这与“保留原有讨论分支”的选择一致。

行锁需要短事务和超时，持锁期间不调用邮件、第三方审核或其他慢服务。锁等待、死锁或超时应按明确策略回滚／有限重试，不返回看似成功的结果。[PostgreSQL 行锁与死锁](https://www.postgresql.org/docs/current/explicit-locking.html)

### 9.3 如果以后确实需要整棵子树删除

必须先区分普通作者的内容删除与管理员的讨论治理，不能让二者共享一个含糊的“删除”语义。

以 B 为根收集后代，需要递归 CTE 或其他可靠的后代索引。只检查 `parent_id=B` 会漏掉孙节点，检查 `root_id=B` 又无法覆盖根为 A 的中间子树。

只把“查询后代”和“删除”放进事务，仍不自动解决并发新增后代问题。所有写入路径必须共享协调机制，例如先锁定讨论根，锁后检查冻结状态；大任务先将该讨论标记为冻结，再分批处理，完成后解除。冻结期间会暂时影响这场讨论中其他正常分支，这是简单协议的代价。

整线程冻结及统一根锁只作为未来批量管理的一个候选，不要求第一版为了单节点清空就把整个热门讨论的写入串行化。大子树操作还需审计、失败续作和恢复策略，不能当作一次普通删除请求无限执行。

## 10. 注册、发布、安全与失败处理

建议采用同源部署：网页与 API 经同一个域名提供，减少跨域 Cookie 配置复杂度。服务端保存会话；Cookie 使用 HttpOnly、Secure 和合理的 SameSite 属性，写接口同时验证 CSRF Token／来源，不把 SameSite 当作全部防护。

登录建议流程：

1. 注册时规范化登录名，检查长度与合法字符；显示名称单独处理。
2. 使用成熟密码库存储 Argon2id 哈希及其参数，不自行实现密码算法。工作参数需要在目标服务器上测量后确定。
3. 登录失败统一给出不泄露具体账号状态的错误，限制账号与来源的尝试频率。
4. 登录成功换发会话；退出时撤销服务端会话；浏览器恢复页面时重新查询当前用户。
5. 第一版若只用用户名和密码且没有邮箱验证，不提供伪装成“已完成”的找回密码功能。面向真实用户前应补充账号恢复方式。

发布与回复的统一流程：

1. 校验登录态和账号状态。
2. 校验正文：例如 1～2000 个 Unicode 码点、拒绝仅空白内容，并设独立的请求体字节上限；最终阈值属于可调整产品参数。
3. 检查提交去重记录；同一用户的同一请求标识，只在约定保留期内创建一次留言。
4. 回复时锁定和检查父节点；根留言没有父节点。
5. 生成可信作者、时间和根 ID，在一个事务内写入留言及去重结果。
6. 返回服务端实际保存的节点，前端再更新列表。网络失败时保留草稿，重试复用原请求标识。

按钮防抖只能减少误点，不能解决“服务器已经保存，但响应在网络中丢失”的重复创建。去重保留期需要明确，例如初始设计 24 小时；过期后不承诺仍能识别同一次历史请求。

第一版纯文本使用文本节点渲染，不能直接塞进 innerHTML；用户名称、正文和错误回显都要采用适合上下文的输出编码。若后续引入 Markdown，应在解析后进行 HTML 净化，并限制链接协议。

参数化查询用于用户输入；排序字段必须映射到固定白名单，不能把前端字符串拼接为 SQL。作者身份只来自会话；即使前端没有显示删除按钮，后端仍必须检查是否为作者或授权管理员。

限流同时考虑账号和来源 IP，并对登录、注册、发帖、读取分页分别设置预算。只按 IP 限制可能误伤校园网、公司网络等共享出口；只按账号限制又容易被批量注册绕过。高风险时再引入验证码，避免第一版对所有正常操作增加摩擦。

## 11. 建议的接口契约与项目组织

以下是设计草案，不是已实现接口。

| 接口职责 | 建议路由 | 关键约束 |
| --- | --- | --- |
| 注册 | `POST /api/auth/register` | 不接受管理员角色等权限字段 |
| 登录 | `POST /api/auth/login` | 创建／轮换 Session，设置安全 Cookie |
| 退出 | `POST /api/auth/logout` | 撤销服务端 Session，受 CSRF 防护 |
| 当前用户 | `GET /api/auth/me` | 只返回展示所需的账号信息 |
| 顶层分页 | `GET /api/comments` | 支持 sort、cursor、limit；只返回顶层 |
| 单条留言 | `GET /api/comments/{id}` | 已删内容返回占位，不泄露旧正文 |
| 直接回复分页 | `GET /api/comments/{id}/replies` | 不包含全部后代；每个父节点独立游标 |
| 发布／回复 | `POST /api/comments` | 正文、可空 parent_id、请求标识；服务端生成作者和根 |
| 删除自己的留言 | `DELETE /api/comments/{id}` | 幂等的正文清空及结构保留 |
| 祖先上下文，P1 | `GET /api/comments/{id}/ancestors` | 分段返回祖先摘要，超出可继续向上加载 |

公共留言对象至少包含：id、user_id、user_name、content、created_at、parent_id、root_id、status、has_children。删除后 content 为空，status 指示删除，由 UI 输出统一占位文案。

列表另附 has_more、next_cursor。接口不需要为了显示分页按钮每次执行全表 COUNT，也不在响应中提供邮箱、IP、密码哈希、会话数据。

建议状态：参数错误 400、未登录 401、无权操作 403、不存在 404、父节点已删或幂等键冲突 409、超限 429。内部错误给用户可重试提示，日志通过请求 ID 定位，不能回显数据库堆栈。

拟定项目职责：

| 位置 | 职责 |
| --- | --- |
| `docs/` | 需求、调研、数据约束、接口约定、验收方案 |
| `frontend/` | 登录界面、留言列表、编辑框、分支加载、状态与错误显示 |
| `backend/auth/` | 注册、密码校验、会话与登录限流 |
| `backend/comments/` | 父子关系校验、发布、分页、删除及并发规则 |
| `backend/common/` | 错误模型、安全过滤、日志、统一配置 |
| `database/migrations/` | 表结构、外键、索引和后续版本迁移 |
| `tests/` | 行为、权限、并发、深链与大数据量验收 |
| `deploy/` | 部署配置、数据库备份与恢复说明 |

上表只是后续组织建议，本次仅创建当前 Markdown 文档，没有创建这些应用模块。第一版采用单体服务加关系数据库即可；Redis、消息队列、微服务和 WebSocket 需要有实际瓶颈或功能需求再引入。

## 12. 风险优先级与验证办法

| 优先级 | 风险 | 触发场景 | 必要控制 | 如何验证 |
| --- | --- | --- | --- | --- |
| 高 | 越权删除或冒充作者 | 修改请求里的 user_id，猜测别人的留言 ID | 会话取作者，后端检查所有权 | 使用甲账号尝试删除乙留言，确认数据没有变化 |
| 高 | 深链导致栈溢出 | 连续上万层回复 | 扁平响应、迭代遍历、分段上下文 | 10000 层链可以分段浏览和继续回复，无整链递归 JSON |
| 高 | 热门讨论响应失控 | 一条根留言有数万回复 | 每个父节点独立分页，严格页大小上限 | 一个根下 50000 个直接子节点，首屏及首次展开仍只返回一页 |
| 高 | 删除后孤儿或误删他人回复 | 删除中间节点、错误使用级联删除 | 默认保留结构，外键保护 | 删除 B 后 C、D 仍在，parent_id 不改变 |
| 高 | 删除／回复竞态 | 两个请求同时访问 B | 共同的行锁和状态复查 | 两种先后顺序都符合第 9 节规则 |
| 高 | XSS／CSRF／注入 | 恶意正文、跨站请求、排序参数 | 文本渲染、CSRF 防护、参数化查询、排序白名单 | 脚本不执行；跨站写失败；恶意参数不改变 SQL 结构 |
| 中 | 深翻页变慢或同时间乱序 | 大量数据、时间戳相同 | 复合索引、时间＋ID 游标 | 静态数据集分页无重复和漏项；查看执行计划 |
| 中 | 重复发帖 | 提交成功后响应丢失，再次点击提交 | 事务内幂等记录 | 同一请求标识并发发送只出现一条留言 |
| 中 | 删除正文再次暴露 | 新增详情、缓存、通知、搜索接口 | 统一可见性处理，派生数据失效 | 所有读接口不再返回旧正文；相关派生副本同步处理 |
| 中 | 孤儿和循环脏数据 | 手工改库、导入、未来移动节点 | 外键、不可改父节点、导入校验和访问检测 | 构造异常关系后工具能检测并停止，不死循环 |
| 中 | 限流误伤正常人 | 多人共享网络出口 | 账号＋IP 组合预算，合理错误提示 | 共享 IP 多账号可正常使用，同时限制单账号滥用 |
| 中 | 数据丢失或恢复错误 | 误操作、数据库故障 | 备份及恢复演练 | 在隔离环境实际恢复，并核对关系及删除状态 |

这些是设计风险，不能表述为应用已经存在或已经修复的漏洞。

## 13. 后续实现的验收清单

功能验收：

- 两个用户能分别注册、登录、退出；重名注册失败；退出后的旧会话不能继续发布。
- 未登录可以阅读，发布／回复／删除被拒绝。
- 正文、用户 ID、名称和创建时间可查看；时间来源可信，名称重复也能区分身份。
- A → B → C → D 保留每条直接父关系；不是全部挂在 A 下。
- 每条 active 留言都可继续回复，包括已有删除祖先但自身仍 active 的留言。
- 删除根、中间节点、叶子节点均符合占位规则；普通用户不能删除别人内容。
- 对已删除节点直接回复得到明确错误；重复删除不产生额外副作用。
- 根排序和同父排序符合约定；同时间多条留言的顺序稳定。
- 每个分支的加载更多互不串游标；错误重试不重复插入节点。
- 草稿在请求失败时保留；长文本、手机窄屏、键盘操作正常。

性能与并发验收采用三种分布，而不只用均匀的“小树”：

| 测试数据 | 主要观察内容 |
| --- | --- |
| 100000 条混合层级留言 | 根列表分页、作者关联、索引使用情况 |
| 一个根下 50000 个直接子节点 | 宽树分页、响应体积、前端按需加载 |
| 一条 10000 层单链 | 深链存储、继续回复、分段导航、无栈溢出 |

上述规模是测试计划，不是产品层级上限，更不是已通过的测试结果。

结构性通过条件：

- 根／直接回复列表的业务数据查询次数有固定预算，建议目标不超过 3 次；会话读取单独统计，不随本页留言数量线性增加数据库往返。
- 查询不为了返回 20 条直接回复而加载整个讨论全部后代。
- 在静态数据集上，逐页遍历结果与一次完整排序的参考集合一致。
- 页面没有随完整树深度增长的递归组件调用或递归 JSON 序列化路径。
- 极端页大小、恶意频繁请求被拒绝或限流，不通过默认返回全部数据“容错”。
- 并发回复／删除、幂等重试、注册唯一约束均有真实数据库测试。

延迟目标可暂定“目标环境下，常规列表 API 在约定负载下 p95 不超过 300ms”，但这是候选验收阈值。开发时先记录 CPU、内存、数据库版本、索引、冷／热缓存、连接池和并发读写比例，再确定正式标准；本次没有测量结果。

还应记录执行计划、扫描／返回行数、响应字节数及前端内存。不能只因为 SQL 查询次数少，就宣称性能已经满足要求。

## 14. 推荐定案与后续顺序

建议先采用以下默认产品规则，后续进入开发前可按需要调整：

| 事项 | 本文建议 |
| --- | --- |
| 使用方式 | 独立单留言板，未登录可读，登录后可写 |
| 账号方式 | 本地用户名＋密码，单独显示名称 |
| 内容格式 | 纯文本与换行；Markdown 后续再加 |
| 回复关系 | 邻接表＋根 ID，父关系不可随意修改 |
| 层级能力 | 不设业务固定层级上限，查询和展示分段 |
| 时间顺序 | 根默认最新优先，同父回复默认最早优先 |
| 删除语义 | 清空自己的正文，保留占位及子回复 |
| 并发边界 | 已删除父节点不能新回复；有效后代仍可继续讨论 |
| 查询策略 | 根分页＋直接子节点分页；复合索引＋游标 |
| 数据库方向 | 优先 PostgreSQL；框架随实际技术栈另行选定 |
| 基础规模 | 单体服务，不提前加入微服务、队列或实时推送 |
| 上线补充 | 管理员治理、备份恢复、账号恢复方式 |

后续适合按“确定这些产品规则 → 数据约束和接口文档 → 账号与单层留言 → 任意层级与分页 → 删除并发及安全 → 数据量与移动端验收”的顺序实施。

本次交付是可供评审的调研和设计依据。所有应用功能、性能数据、运行结果都仍待后续实现与验证。
